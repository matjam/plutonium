# Replace the global fixpoint with SCC summaries

The fastest and most memory-frugal known way to prove that no stack pointer outlives its frame is the design Go's compiler has shipped since 2019: analyze the call graph bottom-up one strongly connected component (SCC) at a time, build a small deref-weighted flow graph per SCC, solve it with a worklist, and keep only a fixed-size per-parameter summary (Go's is 8 bytes) that is written into each package's export data ([Go escape.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/escape/escape.go); [Go leaks.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/escape/leaks.go)). Peak memory under that schedule is bounded by the largest SCC plus the resident summaries, and only recursive SCCs iterate; Plutonium's 22 whole-program passes, 20 GB resident and 1.72 TB allocated are the signature of global re-iteration with rebuilt sets, which every scalable solver in the literature eliminates with worklists, difference propagation and cycle collapse (field-insensitive Andersen on 169K-242K-line C fits in **14-85 MB** ([Hardekopf & Lin PLDI 2007](https://cs.utexas.edu/~lin/papers/pldi07.pdf))). Go's design cannot be copied unchanged, because Go sends every argument of an interface call or unresolved function-value call to the heap ([Go call.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/escape/call.go)), and in a checker that rejects rather than promotes, that rule becomes a compile error at every dynamic call. The missing piece is a sound rule for dynamic boundaries, and the evidence points to a type-level default in the style of Swift's non-escaping closure parameters and Rust's `'static` trait-object default, checked locally at each implementation, with a link-time join over summaries as the fallback if the language must stay rule-free. No surveyed system combines annotation-free inference, rejection instead of promotion, and 100k-line scale, so Plutonium is designing in a gap; the components are all proven, the combination is not.

## The 1.72 TB comes from the schedule, not the problem size

The current analysis behaves like an unspecialized Datalog evaluator without semi-naive deltas: every pass revisits every function, rebuilds token sets and hash indexes, and unions summaries at dynamic calls. Published solvers show what the problem costs once those habits are removed. Hardekopf and Lin's lazy and hybrid cycle detection ran field-insensitive Andersen on Emacs (169K LOC) in **0.56 s and 13.9 MB**, Ghostscript (242K) in **7.99 s and 73.5 MB**, and the 2.17M-line Linux kernel in **87 s and 808 MB**; without cycle detection the larger inputs ran out of 2 GB ([Hardekopf & Lin PLDI 2007](https://cs.utexas.edu/~lin/papers/pldi07.pdf)). Those are peak figures, not totals, so they are not directly comparable to 1.72 TB allocated, but they show that a 120k-line problem fits in tens of megabytes when sets are grown in place rather than rebuilt. Heintze and Tardieu's pre-transitive CLA system went further, answering field-based Andersen on gimp (about 440K lines) in about **1 s and 12 MB** by never materializing the transitive closure and loading object files on demand ([Heintze & Tardieu PLDI 2001](https://prolangs.cs.vt.edu/refs/docs/heintze-pldi2001.pdf)).

Go's escape analysis is the deployed analogue for exactly Plutonium's question. Its solver records two invariants, that pointers to stack objects cannot be stored in the heap and cannot outlive the object (including a loop-scoped variable outliving its iteration), and walks a location graph whose edge weights are dereferences minus address-of operations, clamped at zero so the Bellman-Ford walk has no negative cycles ([Go solve.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/escape/solve.go)). Functions are batched by Tarjan's algorithm into minimal SCCs, bottom-up, and a closure "cannot be the root of a connected component," which forces it into its enclosing function's batch ([Go ir/scc.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/ir/scc.go)). Calls into the same SCC wire arguments straight into the callee's parameter locations, so there is no summary iteration inside a batch; calls to earlier batches, including imported packages, read the callee's tag ([Go call.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/escape/call.go)). When Dempsky's rewrite replaced the older pass, the net/http graph shrank from **12.5M nodes and 5.8M edges to 5.2M locations and 4.8M edges**, and compilebench's Compiler benchmark got about **7% faster** ([golang/go#23109](https://github.com/golang/go/issues/23109)). Go compiles codebases far larger than 120k lines with this pass on every build. No published figure gives Go's escape-analysis time or memory as a share of compile time on a large program, so that remains unmeasured.

The arithmetic for Plutonium follows directly. Under an SCC schedule most components are singletons, each visited once; only recursive SCCs iterate, and they iterate over a finite lattice. If each SCC's graph, worklists and scratch sets live in an arena that is reset after the summary is extracted, total allocation becomes roughly program size times SCC-local iteration count, and peak memory becomes the largest SCC plus all summaries. That last estimate is inference from the Go design and Infer's per-file practice, not a published measurement; Infer's authors state that per-file analysis avoids loading "the entire source program into memory," which "would quickly overspill the RAM" ([Calcagno et al. JACM 2011](https://www.cs.ox.ac.uk/people/hongseok.yang/paper/jacm11-biabduction-webversion.pdf)).

## Ranked approaches for a rejecting, annotation-free, arena-bound checker

The table ranks each technique by fit to six constraints: soundness with rejection, no annotations, interfaces and function values, bounded memory, speed, and cacheable per-package summaries. Rank reflects suitability as a component of Plutonium's checker, not general merit.

### Rank 1: per-SCC summaries are the core, but Go's leak tag is too coarse to reject with

Go's summary is `type leaks [8]uint8`: slot 0 heap, slot 1 "mutator" (flows to the pointer operand of an indirect store), slot 2 "callee," and slots 3-7 for the first five results; each byte holds the minimum dereference count plus one, saturating, and a missing tag parses as a heap leak at depth zero ([Go leaks.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/escape/leaks.go)). Tags travel in export data, written by the unified-IR linker next to inlining data and read back by the importer ([Go noder/linker.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/noder/linker.go); [Go noder/reader.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/noder/reader.go)). Identical tags share one string through `leakTagCache`, a light form of hash-consing ([Go leaks.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/escape/leaks.go)). Blanchet's Java analysis uses the same idea, "integers to represent the escaping parts of values," and spent **6% to 11%** of total compile time on programs up to 363 KB of bytecode, with at most 17 fixpoint iterations and an average of 3.9 per equation "thanks to the splitting of equations systems into strongly connected components" ([Blanchet TOPLAS 2003](https://bblanche.gitlabpages.inria.fr/publications/BlanchetToplas.ps.gz)). Whaley and Rinard computed summaries for the Java class library once, wrote them to files, and reused them for applications, which is the earliest precedent for per-package cached escape summaries ([Whaley & Rinard OOPSLA 1999](https://people.csail.mit.edu/rinard/paper/oopsla99.pdf)).

For Plutonium the vector needs three changes. First, parameter-to-parameter flows (storing `&local` into `*p` where `p` is the caller's pointer) must stay distinct rather than folding into "mutator to heap," which grows the summary to O(params × (params + results)) bytes but keeps it independent of body size. Second, the result-slot cap and field-insensitivity, cheap for an optimizer, are false rejections for a checker; Go treats `x.f = u[0]` as `x = *u` ([Go escape.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/escape/escape.go)), and Choi et al. state that bounding field nodes "can make the result less precise" ([Choi et al. OOPSLA 1999](https://faculty.cc.gatech.edu/~harrold/6340/cs6340_fall2009/Readings/choi99escape.pdf)). Third, the soundness rule for any truncation must be enforced mechanically: saturation, k-limits, slot overflow and field merging may only move a flow to a more-escaping sink, never drop it. Go follows this rule throughout, and it is the property the adversarial reviews should be pointed at, since each unsound acceptance they found is likely a place where a cut lost a flow rather than coarsened it.

Go's own precision also depends on scheduling: its SCC code comments that analysis "can be more precise when analyzing a single non-recursive function than when analyzing a set of mutually recursive functions" ([Go ir/scc.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/ir/scc.go)). Inside an SCC Go merges all members into one graph; that is context-insensitive and cheap, and for a checker it is a known source of false rejections in mutual recursion.

### Rank 2: type-level escape defaults make dynamic calls modular and sound

Every system that scales pays for modularity with signature-level information, either written or defaulted. Swift made closure parameters non-escaping by default in Swift 3 (SE-0103); a closure that is stored must be marked `@escaping`, and the compiler rejects the store otherwise ([SE-0103](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0103-make-noescape-default.md)). Rust defaults `Box<dyn Trait>` to `dyn Trait + 'static`, so values behind a boxed trait object cannot hold borrows unless the type says so ([Rust Reference: lifetime elision](https://doc.rust-lang.org/reference/lifetime-elision.html)). OxCaml infers a two-point locality mode inside a file by constraint solving that "is essentially just transitive closure," and puts the mode into function types, so `List.iter`'s `f` is declared local once and every caller can stack-allocate its closure ([Lorenzen et al. ICFP 2024](https://homepages.inf.ed.ac.uk/slindley/papers/mode-inference.pdf)). OxCaml's cost is annotations at file boundaries: in February 2024, 2,648 of Jane Street's 187,765 `.mli` files used `local` or `global` ([Lorenzen et al. ICFP 2024](https://homepages.inf.ed.ac.uk/slindley/papers/mode-inference.pdf)); it ships no mode polymorphism and reports that this "has not been a significant problem in practice."

The adaptation for Plutonium is a language rule rather than an annotation: views (borrowed pointers into frames) passed as parameters of interface methods or function-typed values do not escape the call, and each implementation and each function literal assigned to such a type is checked locally against that rule; a value that must be retained must be owned and moved. A closure stored in a field, global or interface must not capture frame views. With this rule the summary of a dynamic call is determined by its type, so a package's analysis never depends on downstream implementations, per-package caching survives new implementations, and errors are reported at the implementation that breaks the rule, which is local and explainable. The cost is precision: an implementation that stores an argument view is rejected even if no caller ever passes a stack pointer, which is the same trade Rust makes for trait objects. Because this changes the language's semantics, it is a specification decision for the user, recorded before implementation.

### Rank 3: a thin-link join over summaries keeps inference rule-free at a caching cost

If the language must stay rule-free at interfaces, the sound alternative is closed-world resolution. Whaley and Rinard used "a variant of class hierarchy analysis" but note that "the algorithm can use any conservative approximation" of the call graph, merging the mapped summaries of every potential callee at each call site ([Whaley & Rinard OOPSLA 1999](https://people.csail.mit.edu/rinard/paper/oopsla99.pdf)); Choi et al. and Blanchet take the least upper bound over all CHA targets ([Choi et al.](https://faculty.cc.gatech.edu/~harrold/6340/cs6340_fall2009/Readings/choi99escape.pdf); [Blanchet TOPLAS 2003](https://bblanche.gitlabpages.inria.fr/publications/BlanchetToplas.ps.gz)). Facebook's Zoncolan applies the same "all possible functions a call may resolve to" rule to over 100M lines of Hack and finishes a full analysis in under 30 minutes on a 24-core server ([Distefano et al. CACM 2019](https://6826.csail.mit.edu/2020/papers/facebook-infer-cacm.pdf)). The ThinLTO structure makes this cheap: per-module summaries are merged into a combined index at a "thin link" that reads only summaries, avoiding monolithic LTO, which "is not scalable in time or memory" ([Clang ThinLTO docs](https://clang.llvm.org/docs/ThinLTO.html)).

In Plutonium terms, each package records, per indirect call site, "argument X with deref d flows into a call of signature S," plus a table of its address-taken functions and its method implementations; the link step joins the summaries per signature and checks each recorded flow. The current analysis unions summaries at dynamic calls already, but does it inside the whole-program fixpoint; moving the join to a single post-pass over fixed-size summaries removes it from the iteration. The weakness is that the join is non-local: adding an implementation in package B can reject a call site in package A, and the error must name both. Rapid type analysis, which restricts targets to types that are instantiated, sharpens the join ([Bacon & Sweeney OOPSLA 1996](https://doi.org/10.1145/236337.236371)); CHA is the baseline ([Dean, Grove & Chambers ECOOP 1995](https://doi.org/10.1007/3-540-49538-X_5)).

### Rank 4: solver engineering removes repeated passes without losing precision

Inside each SCC graph, and in any global component such as function-value target sets, four techniques do the work that 22 passes now do by brute force. Difference propagation sends only the part of a set not yet sent: Pereira and Berlin's wave propagation keeps `Pold` per node and a cache per complex constraint, and their depth-first variant had the lowest memory, **1.01x** of Heintze-Tardieu's geometric mean ([Pereira & Berlin CGO 2009](https://homepages.dcc.ufmg.br/~fernando/publications/papers/CGO09.pdf)); semi-naive Datalog evaluation is the same idea. Cycle collapse with union-find stops information circulating; hybrid cycle detection cut propagations by **10x** for Heintze-Tardieu ([Hardekopf & Lin PLDI 2007](https://cs.utexas.edu/~lin/papers/pldi07.pdf)). Offline equivalence detection shrinks the problem before solving: off-line variable substitution cut Andersen's time by **53%** and memory by **59%** on average ([Rountev & Chandra PLDI 2000](https://doi.org/10.1145/349299.349310)), and HRU plus location equivalence removed **79.9%** of constraints and cut memory **3.2-6.9x** ([Hardekopf & Lin SAS 2007](https://www.cs.utexas.edu/~lin/papers/sas07.pdf)). Hash-consed points-to sets store each distinct set once, giving Andersen **1.85x** speed and at least **4.93x** less memory on average for staged flow-sensitive analysis ([Barbar & Sui SAS 2021](https://doi.org/10.1007/978-3-030-88806-0_2)). After the offline reductions, plain sparse bitmaps beat BDDs on both time (1.3x) and memory (1.7x) ([Hardekopf & Lin SAS 2007](https://www.cs.utexas.edu/~lin/papers/sas07.pdf)), which matters because BDD node tables need garbage collection and tuned pools, a poor fit for arenas.

Go's deref-count lattice makes most of this cheaper still: a location's state is a small integer per root, not a set, so propagation is a shortest-path relaxation and terminates because "attributes and the effects propagated from them only grow" ([Go solve.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/escape/solve.go)). The worst case per root group is O(V·E) by the algorithm's structure; Go's source states no bound.

### Ranks 5-8: cheap prefilters, targeted precision, and diagnostics

Unification is the right tool for the parts of the problem where precision matters little. Steensgaard's analysis handled a 75,000-line program in about 27 s on 1996 hardware with almost-linear union-find ([Steensgaard POPL 1996](https://www.cs.cornell.edu/courses/cs711/2005fa/papers/steensgaard-popl96.pdf)), and Das's one-level flow, which keeps directional edges only at the top level of pointer chains, matched Andersen's precision on programs up to 140,000 lines and analyzed 1.4 MLOC in two minutes under 200 MB ([Das PLDI 2000](https://web.eecs.umich.edu/~weimerw/590/reading/das-golf.pdf)). Das's observation that the dominant pointer use is passing addresses to procedures fits stack-escape checking, where most frame addresses enter the graph as arguments. Plutonium can use unification to compute function-value target sets and to discharge the many frames whose addresses never reach anything longer-lived, leaving the directional analysis for the rest. Unification alone is too imprecise as the final arbiter, because every merge is a potential false rejection.

Zipper's lesson applies once false rejections are measured: a context-insensitive pre-analysis finds the few precision-critical methods, and context sensitivity applied only there keeps **98.8%** of 2-object-sensitive precision at a **3.4x** average speedup ([Li et al. OOPSLA 2018](https://cs.au.dk/~amoeller/papers/zipper/paper.pdf)). For Plutonium the likely candidates are generic container helpers and closures called from many sites, where per-call-site specialization of a summary would replace a merged one.

Demand-driven CFL reachability answers single queries cheaply, under 50 KB per query at a 250-node budget ([Sridharan et al. OOPSLA 2005](https://manu.sridharan.net/files/oopsla05.pdf)) and about 0.18 s and 65 KB per query in SUPA ([Sui & Xue, arXiv 1701.05650](https://arxiv.org/pdf/1701.05650)), but every budget exhaustion must be answered "escapes," which in a rejecting checker is a spurious error whose occurrence depends on a tuning constant. Its use in Plutonium is producing witnesses: after the summary pass rejects a site, a backwards walk over summaries with recorded witness edges can explain the path, which answers the ML Kit lesson that inferred lifetimes must be explainable. Sparse flow-sensitive analysis buys precision at real cost: Hardekopf and Lin's SFS handled 1.9 MLOC in 828 s but used **6.4 GB** ([Hardekopf & Lin CGO 2011](https://www.cs.utexas.edu/~lin/papers/cgo11.pdf)). Flow sensitivity matters to Plutonium mainly for loop-scoped variables and reassignment, so it belongs inside individual SCCs where needed, not as the baseline; the Rust project reached the same conclusion when the Datalog Polonius was abandoned because it "has no path to stabilization due to scalability issues," in favor of reachability over a lazily built graph at an accepted 10-20% compile-time cost ([Rust 2025h1 goal](https://rust-lang.github.io/goals/2025h1/Polonius.html); [Rust 2026 goal](https://goals.rust-lang.org/2026/polonius.html)).

### Ranks 9-11: approaches to avoid

General Datalog engines are fast but materialize relations with indexes: Soufflé ran context-insensitive points-to on OpenJDK7 (1.4M variables) in 35 s but used **8.5 GB**, and the context-sensitive analysis used **206.4 GB** ([Jordan et al. CAV 2016](https://souffle-lang.github.io/pdf/cav16.pdf)). Incremental Datalog keeps the full derived relation set resident, and existing incremental frameworks "only support the powerset lattice," so Go's min-deref lattice would need DRedL-style extensions ([Szabó et al. OOPSLA 2018](https://doi.org/10.1145/3276509)). Whole-program region inference is the only fully annotation-free design surveyed, and it is the cautionary case: the ML Kit's 58,000-line AnnoDomini "took one and a half hours to compile," the constraint-based variant was "considerably more space-consuming," and locating a space leak "required a regions expert" ([Tofte et al. HOSC 2004](https://elsman.com/mlkit/pdf/retro.pdf)). Graal's partial escape analysis and HotSpot C2 are intraprocedural after inlining and bail out on budget (C2's `EscapeAnalysisTimeout` defaults to 20 s) ([OpenJDK c2_globals.hpp](https://github.com/openjdk/jdk/blob/master/src/hotspot/share/opto/c2_globals.hpp)); a checker cannot treat a timeout as anything but rejection, so resource bounds must come from the abstract domain, never from a clock.

## Interfaces, closures, generics and iterators each need one fixed rule

Dynamic calls are where Plutonium departs from every deployed system. Go's rule (unknown callee means heap) is sound only because heap allocation is a fallback; its newer handling resolves singly or multiply assigned local function variables statically, and returns "unknown" if any assignment cannot be resolved ([Go call.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/escape/call.go)). Those function-value commits date from April-May 2026 ([Go call.go commit history](https://github.com/golang/go/commits/master/src/cmd/compile/internal/escape/call.go)) and may not be in a released Go version. Swift's optimizer likewise treats a value passed to an unknown callee ("the callee is a closure, class method, etc.") as escaping ([Swift EscapeUtils.swift](https://github.com/swiftlang/swift/blob/main/SwiftCompilerSources/Sources/Optimizer/Utilities/EscapeUtils.swift)), and Clang's lifetime analysis treats unknown calls optimistically, which "can hide real bugs" ([Clang Lifetime Safety docs](https://clang.llvm.org/docs/LifetimeSafety.html)); neither is usable for a sound rejecting checker.

Closures should follow Go: analyze each closure in its creator's SCC, decide capture by value or by reference after the walk (Go captures by value if a variable is not address-taken, never reassigned, and at most 128 bytes ([Go escape.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/escape/escape.go))), and summarize the closure's captured environment as an extra input in its summary. A closure that is called or passed to a non-escaping function parameter stays on the stack with its captures; one stored in a field, global or interface must capture no frame views. OxCaml states the same invariant: "A closure can capture local values only if it is itself local" ([Lorenzen et al. ICFP 2024](https://homepages.inf.ed.ac.uk/slindley/papers/mode-inference.pdf)).

Range-over-func iterators fall out of that rule. The yield function is a function-typed parameter of the iterator; under a non-escaping default for function-typed parameters, the loop body's closure can capture frame locals, and the iterator implementation is checked locally to confirm it calls `yield` but never stores it. Swift's `partial_apply [on_stack]` encodes the same fact, a non-escaping closure context that "cannot escape the callee" ([Swift EscapeUtils.swift](https://github.com/swiftlang/swift/blob/main/SwiftCompilerSources/Sources/Optimizer/Utilities/EscapeUtils.swift)). Whether Go keeps yield closures on the stack only when the iterator is inlined was not verified.

Generics should be summarized once per generic body, not per instantiation, with each type parameter treated as possibly view-bearing. Swift resolves lifetime dependencies "at declaration time, not from the call site's generic context" ([Swift LifetimeAnnotation.md](https://github.com/swiftlang/swift/blob/main/docs/ReferenceGuides/LifetimeAnnotation.md)), and Cyclone's `regions_of(α)` default effect let 110,000 lines of Cyclone code get by with one non-default effect ([Grossman et al. PLDI 2002](https://www.cs.tufts.edu/comp/150BUGS/cyclone-2002.pdf)). Lobster's per-call-site specialization by ownership is the counter-example, unbounded in summary count and resolved by inserting reference counts rather than rejecting ([Lobster memory management](https://aardappel.github.io/lobster/memory_management.html)). If per-body summaries reject too much, Zipper-style selective specialization of the offending generic functions is the bounded remedy.

## Recommended design: four bounded stages and an early-cutoff cache

The direction that best fits every stated constraint has four stages. The first is a per-package, SCC-bottom-up pass over the static call graph (packages form a DAG, so there is no cross-package fixpoint), with closures in their creator's SCC, one deref-weighted location graph per SCC in an arena, a worklist solver with difference propagation and union-find cycle collapse, and a fixed-size summary per function: for each input (parameters, receiver, closure environment), the minimum deref count to each sink in {outlives-caller, each result, each other parameter's pointee}, plus a witness edge per nonzero entry. The arena resets after each SCC; summaries are hash-consed. Only recursive SCCs iterate, over a finite lattice, so termination and cost are known in advance with no timeouts. The second stage applies the dynamic-boundary rule: under the recommended type-level default, interface method calls and function-value calls read a summary fixed by the type, and each implementation, method value and function literal stored into such a type is checked against it in its own package. The third stage, needed only if the type-level rule is rejected or to sharpen precision, is a thin link over summaries that joins per-signature target sets (CHA, refined by RTA or by Steensgaard-style unification of function values) and checks recorded indirect-call flows. The fourth stage is error explanation, a walk back along witness edges that names the chain of summaries responsible for each rejection.

Caching follows Rust's red-green model: a package's key is the hash of its IR and its imports' summaries, and when a recomputed summary hashes identically, dependents are not re-analyzed (early cutoff); rustc marks such a query green "and hence avoid[s] re-executing dependent queries" ([rustc-dev-guide](https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation.html)), and Salsa calls the same move backdating ([Salsa algorithm](https://salsa-rs.github.io/salsa/reference/algorithm.html)). Infer reports the same property: if a procedure group changes, "only it has to be re-analyzed" ([Calcagno et al. JACM 2011](https://www.cs.ox.ac.uk/people/hongseok.yang/paper/jacm11-biabduction-webversion.pdf)). Cached summaries can additionally be validated as post-fixed points in one pass; Abstraction-Carrying Code measured checking at only **1.63x** faster than a well-tuned analysis ([Albert et al. LPAR 2004](https://cliplab.org/papers/lpar04-ai-safety.pdf)), so certificate checking is a consistency check for the cache, not a speed mechanism.

Soundness discipline matters more than any algorithm here, given four reviews that found unsound acceptances. Each abstraction cut (deref saturation, field merging, result-slot overflow, SCC merging, unknown or FFI callee) needs a documented mapping to a more-escaping sink, a missing or unparsable summary must decode as "escapes at depth zero" as Go's does ([Go leaks.go](https://github.com/golang/go/blob/master/src/cmd/compile/internal/escape/leaks.go)), and the two Go invariants (no stack pointer stored in a longer-lived location; no pointer outliving its object, including across loop iterations) should be the checker's stated specification. Each stage is small enough to review in isolation, which the current monolithic fixpoint is not. Expected cost at 120k lines is an inference, not a measurement: Go-scale graphs proportional to IR size, peak memory in the tens to low hundreds of megabytes, and run time comparable to one compiler pass. The first milestone should measure peak arena size per SCC and false-rejection counts on the existing 120k-line program before any precision work.

## Conclusion

The literature changes the framing of Plutonium's problem from "find a faster global solver" to "stop solving globally." The cost explosion and the unsound acceptances share a cause: a single monolithic fixpoint where scheduling, abstraction cuts and dynamic-call unions are entangled, so neither cost nor soundness can be reasoned about locally. Go demonstrates the scheduling and summary format at production scale; Swift, Rust and OxCaml demonstrate that dynamic boundaries are settled by a type-level rule rather than by inference; the points-to literature supplies the solver techniques that make each SCC cheap. What no one has published is the combination of all three with rejection instead of promotion, so Plutonium's real risk is precision, not cost.

That shifts where effort should go. The dynamic-boundary rule is a language decision with larger consequences for users than any solver choice, because it decides which programs are legal, and it should be settled in the specification before the checker is rebuilt. After that, false-rejection counts on the 120k-line corpus become the metric that drives every precision feature (per-field tracking, more result slots, selective specialization, per-SCC flow sensitivity), each added only where measurements show rejections cluster, and each bounded by the domain rather than by a budget.
